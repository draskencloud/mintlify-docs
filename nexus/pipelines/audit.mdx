The audit pipeline is the gateway's **always-on, lossless** compliance and accountability trail. It records every proxied request, every management API mutation, and every policy denial. It cannot be disabled.

For the schema of the Postgres `audit_logs` table and SQL query examples, see [observability/audit-logs](/nexus/observability/audit-logs). For dead-letter file handling, see [observability/dead-letter](/nexus/observability/dead-letter).

---

## Design Principles

### Always-on

The audit pipeline is unconditionally started at gateway boot. There is no `enabled` key for the audit pipeline. This is intentional: audit is a compliance requirement, not an optional feature.

### Lossless (Block overflow policy)

The analytics and logging pipelines drop new events when their buffer is full (**DropNewest**). The audit pipeline instead applies **back-pressure**:

- When the audit buffer is full, the event-sender blocks rather than dropping the event.
- The calling request thread waits until space is available in the buffer.
- This means request latency increases if the audit forwarder falls behind.
- Events are never silently discarded.

| Pipeline | Overflow | Request path impact |
|---|---|---|
| Audit | **Block** | Latency increases if audit backs up |
| Analytics | DropNewest | None — events silently dropped |
| Logging | DropNewest | None — records silently dropped |

### Graceful drain on shutdown

The shutdown sequence guarantees no audit records are lost:

1. Proxy port stops accepting new connections.
2. In-flight requests complete.
3. **Audit pipeline drains** — all buffered events are delivered to the forwarder.
4. Database pool closes.
5. Process exits.

If the Postgres forwarder is unreachable during drain, records are written to the dead-letter file.

## Default Forwarder: Postgres

When no `[[audit.forwarders]]` are configured, the gateway automatically activates a Postgres forwarder that writes to the `audit_logs` table.

```
No [[audit.forwarders]] configured
    → Auto-activates postgres forwarder
        → Writes to audit_logs table
```

### `audit_logs` table schema

```sql
CREATE TABLE audit_logs (
    id                  UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
    app_id              UUID        REFERENCES apps(id) ON DELETE SET NULL,
    token_id            UUID        REFERENCES api_tokens(id) ON DELETE SET NULL,
    method              TEXT        NOT NULL,
    path                TEXT        NOT NULL,
    status_code         INTEGER     NOT NULL,
    latency_ms          BIGINT      NOT NULL,
    timestamp           TIMESTAMPTZ NOT NULL DEFAULT now(),
    client_ip           TEXT,
    user_agent          TEXT,
    request_body_hash   TEXT,
    response_body_hash  TEXT
);
```

Indexes are automatically created on `app_id`, `token_id`, and `timestamp DESC` for efficient querying.

## Configuration

The audit pipeline has no `enabled` key. All other pipeline parameters are configurable.

```toml
[audit]
# In-memory ring buffer capacity. When full, inbound requests block.
# Increase for high-throughput deployments.
buffer_size        = 10000   # env: GATEWAY_AUDIT__BUFFER_SIZE

# Records sent to the forwarder per batch.
batch_size         = 500     # env: GATEWAY_AUDIT__BATCH_SIZE

# Maximum time between flushes (milliseconds).
flush_interval_ms  = 5000    # env: GATEWAY_AUDIT__FLUSH_INTERVAL_MS

# Retries before writing to dead-letter.
retry_max_attempts = 3       # env: GATEWAY_AUDIT__RETRY_MAX_ATTEMPTS

# Initial retry backoff (milliseconds); doubles per attempt.
retry_backoff_ms   = 200     # env: GATEWAY_AUDIT__RETRY_BACKOFF_MS

# Path for records that exhausted all retries.
dead_letter_path   = "logs/audit_dead_letter.jsonl"  # env: GATEWAY_AUDIT__DEAD_LETTER_PATH
```

### Capacity planning

| Metric | Formula |
|---|---|
| Memory per event | ~2 KB |
| Buffer memory at default | ~20 MB |
| Max sustained event rate (default) | `buffer_size / (batch_size / flush_interval_ms)` ≈ 100 events/sec before back-pressure |
| Postgres insert capacity | ~1,000–5,000 rows/sec depending on hardware and WAL settings |

For a gateway handling more than 1,000 requests/second, increase `buffer_size` to at least 50,000 and tune `batch_size` to 2,000–5,000. Ensure the Postgres connection pool (`db_max_connections`) is large enough to service audit writes alongside API queries.

## Custom Forwarders

The auto-configured Postgres forwarder is sufficient for most deployments. Custom forwarders can be added if needed (e.g., shipping audit records to a secondary Postgres replica, a webhook, or a file for archival).

```toml
# Use the auto-configured postgres forwarder plus a file archive
[[audit.forwarders]]
name              = "postgres"
type              = "postgres"
enabled           = true
batch_size        = 500
flush_interval_ms = 5000

[[audit.forwarders]]
name              = "archive"
type              = "file"
enabled           = true
path              = "/mnt/audit-archive/audit.jsonl"
max_mb            = 2000
max_days          = 365
compress          = true
```

> When any `[[audit.forwarders]]` block is present, the auto-configured postgres forwarder is **not** created. You must explicitly include a postgres forwarder if you want database storage.

## SQL Query Examples

### Requests per token (last 24 hours)

```sql
SELECT
    t.name,
    t.id,
    COUNT(*) AS request_count,
    SUM(CASE WHEN al.status_code >= 400 THEN 1 ELSE 0 END) AS error_count
FROM audit_logs al
JOIN api_tokens t ON al.token_id = t.id
WHERE al.timestamp > now() - INTERVAL '24 hours'
GROUP BY t.name, t.id
ORDER BY request_count DESC;
```

### Error spike detection

```sql
SELECT
    date_trunc('minute', timestamp) AS minute,
    COUNT(*) FILTER (WHERE status_code >= 500) AS server_errors,
    COUNT(*) FILTER (WHERE status_code = 429) AS rate_limited,
    COUNT(*) AS total
FROM audit_logs
WHERE timestamp > now() - INTERVAL '2 hours'
GROUP BY 1
ORDER BY 1;
```

### Latency percentiles by application

```sql
SELECT
    a.slug,
    COUNT(*) AS requests,
    ROUND(percentile_cont(0.50) WITHIN GROUP (ORDER BY al.latency_ms)) AS p50_ms,
    ROUND(percentile_cont(0.95) WITHIN GROUP (ORDER BY al.latency_ms)) AS p95_ms,
    ROUND(percentile_cont(0.99) WITHIN GROUP (ORDER BY al.latency_ms)) AS p99_ms
FROM audit_logs al
JOIN apps a ON al.app_id = a.id
WHERE al.timestamp > now() - INTERVAL '1 hour'
GROUP BY a.slug
ORDER BY p99_ms DESC;
```

### Recent requests for a specific client IP

```sql
SELECT timestamp, method, path, status_code, latency_ms, token_id
FROM audit_logs
WHERE client_ip = '203.0.113.42'
  AND timestamp > now() - INTERVAL '1 hour'
ORDER BY timestamp DESC
LIMIT 50;
```

### Requests to a specific path pattern

```sql
SELECT timestamp, method, status_code, latency_ms, client_ip
FROM audit_logs
WHERE path LIKE '/my-api/v1/users/%'
  AND timestamp > now() - INTERVAL '6 hours'
ORDER BY timestamp DESC
LIMIT 100;
```

## Metrics

| Metric | Type | Labels | Description |
|---|---|---|---|
| `gateway_audit_buffer_size` | Gauge | `forwarder` | Current events in buffer. Alert if sustained above 80% of `buffer_size`. |
| `gateway_audit_delivery_failures_total` | Counter | `forwarder`, `reason` | Delivery failures (back-pressure means failures eventually reach dead-letter, not /dev/null). |

### Alert examples

```yaml
- alert: AuditBufferHigh
  expr: gateway_audit_buffer_size > 8000
  for: 30s
  labels:
    severity: critical
  annotations:
    summary: "Audit buffer at {{ $value }}/10000 — request latency increasing"
    description: "The audit pipeline cannot keep up with the request rate. Check Postgres performance and connection pool size."

- alert: AuditDeliveryFailures
  expr: rate(gateway_audit_delivery_failures_total[5m]) > 0
  for: 1m
  labels:
    severity: critical
  annotations:
    summary: "Audit forwarder delivery failures: {{ $labels.reason }}"
    description: "Audit records may be accumulating in the buffer or dead-letter file."
```

## Frequently Asked Questions

**Can I disable the audit pipeline for testing?**

No. The audit pipeline starts unconditionally. In test environments, you can point `database_url` to a SQLite in-memory database or a test Postgres database. The audit forwarder will write there instead of your production database.

**Will the audit pipeline cause request failures if Postgres is down?**

Yes, eventually. While Postgres is unavailable, the audit buffer fills up. Once full, the Block policy causes requests to stall waiting for buffer space. After `retry_max_attempts` are exhausted, records go to `dead_letter_path`. If the dead-letter path is also unavailable (e.g., disk full), the pipeline logs an error.

Design your deployment so Postgres is a HA service (e.g., RDS Multi-AZ, Patroni) to avoid this scenario.

**Can I query audit logs via the management API?**

Not in v1. Query Postgres directly using the SQL examples above, or use a database GUI tool.

**How long should I retain audit logs?**

That depends on your compliance requirements (SOC 2, PCI-DSS, HIPAA, etc.). Typical retentions are 90 days to 7 years. Implement a Postgres partition or archival job to manage retention. The `timestamp` index supports efficient range-delete operations.
