Nexus API Gateway by Drasken Cloud enforces authentication at the policy level. Every request that enters the proxy port (`:8080`) passes through the authentication middleware before it reaches a backend. This document explains how authentication is configured, where it sits in the middleware stack, what it produces, and how access control is enforced downstream.

## Policy-Level Configuration

Authentication is not a global on/off switch. It is configured per **policy**, and policies are attached at any level of the App → Version → Revision → Endpoint hierarchy. The most specific policy wins.

```
App
└── Version
    └── Revision          ← policy here applies to all endpoints in this revision
        └── Endpoint      ← policy here overrides the revision-level policy for this path
```

This means you can:

- Require JWT auth for an entire revision, but disable auth for a single public health-check endpoint.
- Use API key auth for most endpoints but require JWT with specific claims for an admin endpoint.
- Allow unauthenticated read traffic while requiring write auth only for `POST`/`PUT`/`DELETE` endpoints.

## AuthPolicy Reference

The `AuthPolicy` object is embedded in the policy JSONB column. All fields are optional; omitting a field inherits from the parent level.

| Field | Type | Description |
|---|---|---|
| `auth_type` | `"api_key"` \| `"jwt"` \| `"basic"` \| `"none"` | Selects the authentication backend. Required when auth is enabled. |
| `required` | `bool` | If `true` (default), unauthenticated requests receive `401`. If `false`, unauthenticated requests are allowed through with a generic identity. |
| `jwt_secret_env` | `string` | **HS256 only.** Name of the environment variable that holds the plaintext JWT secret. The secret is never placed in the config file. |
| `jwt_public_key_env` | `string` | **RS256/RS384/RS512/ES256/ES384.** Name of the environment variable containing the PEM-encoded public key. |
| `jwks_url` | `string` | **RS256/RS384/RS512/ES256/ES384.** URL of a JWKS endpoint. Used instead of `jwt_public_key_env` when keys are served remotely (e.g., Auth0, Keycloak). |
| `issuer` | `string` | Expected `iss` claim. If set, the gateway validates that the token's `iss` matches exactly. |
| `audience` | `string` | Expected `aud` claim. If set, the gateway validates that the token's `aud` contains this value. |
| `required_claims` | `string[]` | List of claim names that must be present in the JWT payload. Any missing claim results in `401`. |
| `forward_claims_as_headers` | `map<string, string>` | Maps JWT claim names to request header names. Matching claims are forwarded to the backend as HTTP headers after successful validation. |
| `backend_mtls_profile` | `string` | Name of the mTLS profile to use when connecting to the backend after auth. Profiles are configured via environment variables at startup. |

### Example Policy (JSON)

```json
{
  "auth_type": "jwt",
  "required": true,
  "jwks_url": "https://auth.example.com/.well-known/jwks.json",
  "issuer": "https://auth.example.com/",
  "audience": "my-api",
  "required_claims": ["sub", "org_id"],
  "forward_claims_as_headers": {
    "sub": "X-User-Id",
    "org_id": "X-Org-Id"
  }
}
```

## Middleware Stack Position

Every request passes through the middleware stack in this fixed order, from outermost to innermost:

```
Per-IP rate limit
  → Trace context
    → Authentication              ← credential validated here
      → Per-token rate limit      ← keyed off the validated identity
        → Header validation
          → IP filter
            → Body size limit
              → Timeout
                → CORS
                  → Access logger
                    → Proxy engine
```

**Before auth:**

- **Per-IP rate limit** runs first so that unauthenticated flood attacks are dropped cheaply before any credential validation work.
- **Trace context** attaches a request ID and span to every request, regardless of auth outcome.

**Auth layer responsibilities:**

1. Extract the credential from the request (Bearer token, JWT, Basic header).
2. Validate the credential against the configured `auth_type`.
3. Produce an authenticated identity on success.
4. Return `401 Unauthorized` or `403 Forbidden` on failure.
5. Attach the identity to the request so downstream layers and the proxy engine can read it.

**After auth:**

- The **per-token rate limit** uses the validated identity (token ID, or username for basic auth) as the rate limit key, enabling per-token quota enforcement.
- All other middleware and the proxy engine assume a valid identity is present when `required = true`.

## The Authenticated Identity

On successful authentication, the gateway derives an authenticated identity for the request and carries it through the rest of the middleware stack. The identity has the following fields:

| Field | Description |
|-------|-------------|
| `app_id` | The App this credential belongs to |
| `token_id` | For API key and JWT: the token's ID. For Basic auth: the credential's ID. Absent when `required = false` and no credential was presented |
| `username` | For Basic auth: the authenticated username |
| `scopes` | Scopes granted by this credential |

The gateway uses the identity to:

- Log the token ID in the audit log for every proxied request.
- Enforce scope rules before forwarding.
- Use the token ID as the per-token rate limit key.

## Scope Enforcement

After authentication succeeds, the gateway enforces **method-based scope rules**:

| HTTP Method | Required Scope |
|---|---|
| `GET` | `proxy:read` |
| `HEAD` | `proxy:read` |
| `OPTIONS` | `proxy:read` |
| `POST` | `proxy:write` |
| `PUT` | `proxy:write` |
| `PATCH` | `proxy:write` |
| `DELETE` | `proxy:write` |

If the authenticated credential does not carry the required scope, the gateway returns:

```http
HTTP/1.1 403 Forbidden
Content-Type: application/json

{"status":403,"message":"insufficient scope","data":null}
```

**JWT scope extraction:** For JWT auth, scopes are read from a configurable claim (default: `scope` or `scopes`). The claim value may be a space-delimited string or a JSON array.

**Override with `required_scopes`:** A policy may set `required_scopes` to an explicit list. An empty array (`[]`) disables scope enforcement entirely for that policy level — useful for endpoints where any authenticated caller is acceptable regardless of scope.

## Unauthenticated Pass-Through (`required = false`)

Setting `required = false` in an `AuthPolicy` allows requests with no credential (or an invalid credential) to proceed:

```json
{
  "auth_type": "api_key",
  "required": false
}
```

When a request arrives without a credential and `required = false`:

- The gateway does **not** attempt credential validation.
- A generic anonymous identity is produced with no token ID, no username, and no scopes.
- The request proceeds through the rest of the middleware stack and is forwarded to the backend.
- Scope enforcement is also relaxed: if the identity has no scopes and `required = false`, the 403 scope check is skipped.

When a credential **is** presented but fails validation, and `required = false`:

- The gateway still returns `401`. A malformed or expired credential is always rejected; `required = false` only permits the absence of any credential.

**Use cases for `required = false`:**

- Public read APIs where anonymous access is allowed but authenticated users get additional capabilities.
- Gradual auth rollout: enable `required = false` first to measure traffic before enforcing auth.
- Webhook receivers where the caller is identified by payload signature rather than HTTP auth.

## Auth Methods Summary

| Method | Header | Credential Storage | Caching | Best For |
|---|---|---|---|---|
| `api_key` | `Authorization: Bearer <token>` | SHA-256 hash in PostgreSQL | Redis with configurable TTL | Machine-to-machine, third-party integrations |
| `jwt` | `Authorization: Bearer <jwt>` | Not stored (stateless) | JWKS key set only; no per-token cache | User-facing APIs, federated identity providers |
| `basic` | `Authorization: Basic <base64>` | bcrypt hash in PostgreSQL | Redis with configurable TTL | Legacy clients, simple service-to-service |
| `none` | — | — | — | Public endpoints, internal health checks |
