This document covers the full lifecycle of an API through the gateway: from creating the App to routing live traffic, through versioning strategies, revision promotion, rollback, and deactivation.

---

## Full Lifecycle

```
1. Create App            → defines routing mode and base gateway path
2. Create Version        → supply backend fields to auto-create rev-1 (activated instantly)
   └─ [system] rev-1 created and activated automatically
3. Traffic flows immediately — no separate revision step required
4. Deploy new backend → POST /revisions → POST /revisions/:id/activate
5. Rollback            → POST /revisions/<older_id>/activate (one call)
6. Inspect history     → GET /revisions (newest → oldest; is_current marks live)
7. Deprecate Version   → signal clients to migrate; traffic continues
8. Retire Version      → traffic stops; 404 returned for all paths
9. Deactivate App      → 503 returned for all app paths
```

---

## What is a Revision?

A Revision is an **immutable, append-only snapshot** of a backend target at a specific point in time. Every change to the backend (new host, new port, new policy) creates a new Revision row — the old one is never deleted.

| Property | Value |
|----------|-------|
| Storage | Full snapshot per row — no diffs, no reconstruction |
| Deletion | Not allowed (`DELETE /revisions/:id` returns `405`) |
| Current marker | `is_current: true` on exactly one revision per version |
| Rollback | Re-activate any prior revision via `POST …/activate` |
| History | `GET …/revisions` returns all revisions ordered newest → oldest |

This design means your deployment history is always intact. Rolling back to any prior state is a single API call.

## Step-by-Step: From App to First Request

### 1. Create the App

```bash
curl -s -X POST http://localhost:9090/api/v1/apps \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Orders Service",
    "slug": "orders",
    "gateway_path": "/orders",
    "routing_mode": "managed_endpoint",
    "default_policy": {
      "auth": { "auth_type": "api_key", "required": true },
      "rate_limit": { "enabled": true, "requests": 1000, "window_seconds": 60 }
    }
  }' | jq .data.id
```

Save the returned UUID as `APP_ID`.

### 2. Create Version v1 (with auto-revision)

Supply backend fields on version create and the gateway auto-creates `rev-1`, activates it, and returns both objects in a single response:

```bash
curl -s -X POST "http://localhost:9090/api/v1/apps/$APP_ID/versions" \
  -H "Content-Type: application/json" \
  -d '{
    "version": "v1",
    "backend_scheme": "https",
    "backend_host": "orders.internal.cluster.local",
    "backend_port": 443,
    "backend_base_path": "/",
    "strip_gateway_path": true,
    "health_check_path": "/health"
  }'
```

Response shape:

```json
{
  "status": 201,
  "message": "created",
  "data": {
    "version": { "id": "<VERSION_ID>", "version": "v1", ... },
    "initial_revision": { "id": "<REVISION_ID>", "revision": "rev-1", "is_current": true, ... }
  }
}
```

Save `data.version.id` as `VERSION_ID` and `data.initial_revision.id` as `REVISION_ID`.

Traffic is already flowing — steps 3 and 4 from the old flow (create revision, activate revision) are handled automatically.

<Note>
  If you omit `backend_host`, the version is created without a revision. You can add revisions manually at any time via `POST …/revisions`.
</Note>

### 3. Issue an API Token

```bash
curl -s -X POST "http://localhost:9090/api/v1/apps/$APP_ID/tokens" \
  -H "Content-Type: application/json" \
  -d '{ "name": "production-token", "scopes": ["proxy:read", "proxy:write"] }' \
  | jq .data.token
# "gw_abc123..."
```

### 4. Register Endpoints (managed_endpoint mode)

```bash
for endpoint in \
  '{"method":"GET","path":"/","backend_path":"/"}' \
  '{"method":"POST","path":"/","backend_path":"/"}' \
  '{"method":"GET","path":"/{id}","backend_path":"/{id}"}' \
  '{"method":"PUT","path":"/{id}","backend_path":"/{id}"}' \
  '{"method":"DELETE","path":"/{id}","backend_path":"/{id}"}'; do
  curl -s -X POST \
    "http://localhost:9090/api/v1/apps/$APP_ID/versions/$VERSION_ID/revisions/$REVISION_ID/endpoints" \
    -H "Content-Type: application/json" \
    -d "$endpoint" | jq .data.id
done
```

### 5. Make the First Proxied Request

```bash
API_TOKEN=gw_abc123...

curl -s http://localhost:8080/orders/v1/ \
  -H "Authorization: Bearer $API_TOKEN" | jq
```

## Revision Promotion (Deploying a New Backend)

When deploying a new version of your backend service, create a new Revision and activate it. The old revision stays registered as a rollback target — it is never deleted.

```bash
# Step 1: Create new revision pointing at the new backend
NEW_REVISION_ID=$(curl -s -X POST \
  "http://localhost:9090/api/v1/apps/$APP_ID/versions/$VERSION_ID/revisions" \
  -H "Content-Type: application/json" \
  -d '{
    "revision": "rev-2",
    "backend_scheme": "https",
    "backend_host": "orders-v2.internal.cluster.local",
    "backend_port": 443,
    "backend_base_path": "/",
    "strip_gateway_path": true
  }' | jq -r .data.id)

# Step 2: Activate the new revision (traffic switches immediately)
curl -s -X POST \
  "http://localhost:9090/api/v1/apps/$APP_ID/versions/$VERSION_ID/revisions/$NEW_REVISION_ID/activate" \
  | jq
```

After activation:
- `rev-2.is_current = true` — all stable traffic goes here
- `rev-1.is_current = false` — retained in history; available for rollback
- The revision table retains both records; no data is deleted

## Rollback

Rolling back means activating any prior revision. No new revision creation is required:

```bash
# Activate the previous revision (rev-1 in this example)
curl -s -X POST \
  "http://localhost:9090/api/v1/apps/$APP_ID/versions/$VERSION_ID/revisions/$REVISION_ID/activate" \
  | jq
```

The route cache is invalidated immediately; traffic switches back within milliseconds.

To find the ID of the revision you want to roll back to, inspect the history:

```bash
curl -s \
  "http://localhost:9090/api/v1/apps/$APP_ID/versions/$VERSION_ID/revisions" \
  | jq '.data[] | {id, revision, is_current, created_at}'
```

## Revision History

`GET …/revisions` returns all revisions for a version, ordered newest first. The `is_current` field marks which revision is currently serving traffic.

```bash
curl -s \
  "http://localhost:9090/api/v1/apps/$APP_ID/versions/$VERSION_ID/revisions" \
  | jq '.data[] | { revision, is_current, backend_host, created_at }'
```

Example output:

```json
{ "revision": "rev-3", "is_current": true,  "backend_host": "orders-v3.internal", "created_at": "2026-05-10T..." }
{ "revision": "rev-2", "is_current": false, "backend_host": "orders-v2.internal", "created_at": "2026-05-08T..." }
{ "revision": "rev-1", "is_current": false, "backend_host": "orders-v1.internal", "created_at": "2026-05-01T..." }
```

Any row can be re-activated for instant rollback.

## OpenAPI Endpoint Sync

In `managed_endpoint` mode, you can populate a revision's endpoints automatically from an upstream OpenAPI specification:

```bash
curl -s -X POST \
  "http://localhost:9090/api/v1/apps/$APP_ID/versions/$VERSION_ID/revisions/$REVISION_ID/sync-openapi" \
  -H "Content-Type: application/json" \
  -d '{ "openapi_url": "https://orders.internal/openapi.json" }'
```

Or supply the spec inline:

```bash
curl -s -X POST \
  "http://localhost:9090/api/v1/apps/$APP_ID/versions/$VERSION_ID/revisions/$REVISION_ID/sync-openapi" \
  -H "Content-Type: application/json" \
  -d '{ "openapi_spec": { ...OpenAPI JSON object... } }'
```

The gateway parses all `paths` from the spec and upserts them as endpoints on the revision. The operation is idempotent — calling it twice with the same spec produces no duplicate rows.

Response:

```json
{ "synced": 12, "skipped": 0, "errors": [] }
```

<Note>
  OpenAPI sync is only available on `managed_endpoint` mode revisions. It returns `422` on `pass_through` revisions.
</Note>

## Multiple Simultaneous Active Versions

The gateway supports multiple Version objects in `active` status for the same App at the same time. `v1` and `v2` can coexist and both serve traffic:

```
/orders/v1  →  Version v1 (status: active)  →  Revision rev-3 (is_current)
/orders/v2  →  Version v2 (status: active)  →  Revision rev-1 (is_current)
```

This enables zero-downtime API versioning: deploy v2 alongside v1, migrate clients incrementally, then retire v1 when migration is complete.

```bash
# Create v2 alongside existing v1 (auto-creates rev-1 for v2)
curl -s -X POST "http://localhost:9090/api/v1/apps/$APP_ID/versions" \
  -H "Content-Type: application/json" \
  -d '{
    "version": "v2",
    "backend_host": "orders-v2.internal.cluster.local",
    "backend_port": 443
  }' | jq
```

## Version Status Lifecycle

```
active → deprecated → retired
```

| Transition | API call | Effect |
|-----------|---------|--------|
| Mark as deprecated | `PATCH .../versions/:id` with `{"status": "deprecated"}` | Traffic continues; `Deprecation: true` response header added |
| Retire version | `PATCH .../versions/:id` with `{"status": "retired"}` | All requests to paths under this version return `404`; revision caches invalidated immediately |
| Retire → active | Not supported | Create a new version |

### Deprecation header

When a Version is in `deprecated` status, every response from that version includes:

```
Deprecation: true
```

This header signals to client developers that they need to migrate. Clients that ignore it will break when the version is eventually retired.

## App Deactivation

Deactivating an App stops all traffic to that app instantly — across all versions and revisions.

```bash
curl -s -X PATCH "http://localhost:9090/api/v1/apps/$APP_ID" \
  -H "Content-Type: application/json" \
  -d '{"is_active": false}' | jq
# All requests to /orders/* now return 503
```

Reactivating:

```bash
curl -s -X PATCH "http://localhost:9090/api/v1/apps/$APP_ID" \
  -H "Content-Type: application/json" \
  -d '{"is_active": true}' | jq
```

App deactivation does not delete any data. All tokens, versions, revisions, and endpoints remain intact and resume functioning when the app is reactivated.

---

## Hard Delete vs Soft Delete

| Operation | API call | Effect |
|-----------|---------|--------|
| Deactivate App | `PATCH /apps/:id` with `{"is_active": false}` | Traffic stops; data preserved |
| Delete App | `DELETE /apps/:id` | App and all children cascade-deleted; tokens deleted; audit log `app_id` set to NULL |
| Retire Version | `PATCH .../versions/:id` with `{"status": "retired"}` | Traffic stops under this version; data preserved |
| Delete Version | `DELETE .../versions/:id` | Version and all revisions and endpoints deleted |
| Delete Revision | `DELETE .../revisions/:id` | **405 Method Not Allowed** — revisions are immutable; retire the version or activate an older revision instead |

Prefer soft operations (deactivate / deprecate / retire) in production. Hard deletes on apps and versions are not reversible.

## Listing and Inspecting

```bash
# All apps
curl -s http://localhost:9090/api/v1/apps | jq

# Versions for an app
curl -s "http://localhost:9090/api/v1/apps/$APP_ID/versions" | jq

# Full revision history for a version (newest first)
curl -s "http://localhost:9090/api/v1/apps/$APP_ID/versions/$VERSION_ID/revisions" | jq

# Which revision is currently active?
curl -s "http://localhost:9090/api/v1/apps/$APP_ID/versions/$VERSION_ID/revisions" \
  | jq '.data[] | select(.is_current == true)'
```

## Common Mistakes

| Mistake | Consequence | Fix |
|---------|------------|-----|
| Creating a version without backend fields and expecting traffic | No traffic; no revision exists yet | Add `backend_host` to version create, or create a revision manually |
| Trying to delete a revision | `405 Method Not Allowed` | Revisions are immutable; activate an older revision to roll back, or retire the version to stop traffic |
| Retiring a version before clients have migrated | All clients break immediately | Use `deprecated` first; give clients time |
| Setting `is_current` by editing the record directly | Bypasses cache invalidation | Always use the `/activate` endpoint |
| Forgetting to activate a manually created revision | No traffic flows; `404` on all paths | `POST .../revisions/:id/activate` |
