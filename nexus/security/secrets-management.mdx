## Core Principle: 12-Factor Secrets

The gateway follows the [12-factor app](https://12factor.net/config) pattern for configuration:

> **Store config in the environment.**

The TOML configuration file (`config/default.toml`) contains **non-secret settings only** — timeouts, pool sizes, ports, feature flags, cache TTLs. Every secret — tokens, passwords, private keys, connection strings with credentials — is provided via an **environment variable** at runtime.

```
config/default.toml     ← non-secret settings (safe to commit)
.env (local dev only)   ← never commit; in .gitignore
process environment     ← set by CI/CD, container runtime, secrets manager
```

## What Is a Secret?

| Category | Examples | Secret? |
|---|---|---|
| Auth signing material | JWT secrets, RSA/EC private keys | Yes |
| Auth verification material | RSA/EC public keys | Yes (controls who you trust) |
| Database credentials | username, password, connection string | Yes |
| Cache credentials | Redis password | Yes |
| Admin API token | `GATEWAY_SERVER__ADMIN_TOKEN` value | Yes |
| TLS certificate private key | `GATEWAY_TLS_KEY_PATH` target file | Yes |
| mTLS client private key | `GATEWAY_MTLS_PROFILE_*_KEY_PATH` target file | Yes |
| Port numbers | `8080`, `9090` | No |
| Timeouts | `5000ms`, `30s` | No |
| Cache TTLs | `300s` | No |
| Feature flags | `true`/`false` | No |

## JWT Secrets and Public Keys

The `AuthPolicy` stored in the database **contains the name of an environment variable**, not the secret value itself.

**HS256 (symmetric secret):**

```json
{
  "auth_type": "jwt",
  "jwt_secret_env": "MYAPP_JWT_SECRET"
}
```

At startup, the gateway reads `process.env["MYAPP_JWT_SECRET"]`. If the variable is not set, the gateway fails with a configuration error.

```bash
# Set the actual secret value in the environment
export MYAPP_JWT_SECRET="a-random-256-bit-or-longer-secret-value"
```

**RS256 / ES256 (public key from PEM):**

```json
{
  "auth_type": "jwt",
  "jwt_public_key_env": "MYAPP_JWT_PUBLIC_KEY"
}
```

```bash
# Set the env var to the full PEM content
export MYAPP_JWT_PUBLIC_KEY="$(cat /run/secrets/jwt-public-key.pem)"
```

The environment variable must contain the complete PEM block:

```
-----BEGIN PUBLIC KEY-----
MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEA...
-----END PUBLIC KEY-----
```

**Why the indirection?** Storing the env var name (not the value) in the database means:

- The database never contains key material.
- You can rotate the key by updating the env var and restarting the gateway, without a database migration.
- Different environments (dev, staging, prod) use different env var values for the same env var name, and the policy record is identical across environments.
- The database can be inspected (or even exported for debugging) without exposing secrets.

## Admin Token

```bash
export GATEWAY_SERVER__ADMIN_TOKEN="$(openssl rand -base64 48)"
```

When set, all requests to port `9090` must include `Authorization: Bearer <value>`.

**If not set:** The management API is unauthenticated. Acceptable in local development behind a firewall, but never in production.

Generate a strong admin token:

```bash
# 48 bytes of random → 64 character base64 string
openssl rand -base64 48

# Or with Python
python3 -c "import secrets; print(secrets.token_urlsafe(48))"
```

Store it in your secrets manager and inject it into the gateway's environment at startup. Never hardcode it in a Dockerfile, shell script, or CI config file.

## Database Credentials

Embed credentials in the `DATABASE_URL` environment variable using the standard PostgreSQL connection string format:

```bash
export DATABASE_URL="postgres://myuser:mysecretpassword@db.internal:5432/gateway_prod?sslmode=require"
```

**Format:** `postgres://<user>:<password>@<host>:<port>/<database>[?<options>]`

| Component | Notes |
|---|---|
| `<user>` | Database user (URL-encode special characters with `%XX`) |
| `<password>` | Database password (URL-encode special characters) |
| `<host>` | Hostname or IP of the PostgreSQL server |
| `<port>` | PostgreSQL port (default: `5432`) |
| `<database>` | Database name |
| `sslmode=require` | Enforce TLS for the database connection |

**In config/default.toml:**

```toml
[database]
# Database connection URL is set via environment variable
# env: DATABASE_URL
# url = ""  ← do not put credentials here
```

The config file should never contain a `url` value with embedded credentials. The `DATABASE_URL` environment variable overrides any value in the config file.

## Redis Credentials

```bash
# Unauthenticated Redis (dev only)
export GATEWAY_CACHE__REDIS__URL="redis://localhost:6379"

# Authenticated Redis
export GATEWAY_CACHE__REDIS__URL="redis://:mysecretpassword@redis.internal:6379"

# TLS + authenticated Redis
export GATEWAY_CACHE__REDIS__URL="rediss://:mysecretpassword@redis.internal:6380"
```

**URL format:**

| Scheme | Meaning |
|---|---|
| `redis://` | Plain TCP connection |
| `rediss://` | TLS-encrypted connection |

The password appears after the second colon in `redis://:password@host`. URL-encode special characters in the password.

In production, always use `rediss://` to encrypt cache traffic, and always set a Redis password (`requirepass` in `redis.conf`).

## mTLS Client Certificates

When the gateway connects to a backend using mTLS, it presents a client certificate to prove its identity. Certificate and key file paths are configured via environment variables, not embedded in config files:

```bash
# Profile named "internal" — used when backend_mtls_profile = "internal"
export GATEWAY_MTLS_PROFILE_INTERNAL_CERT_PATH="/run/secrets/gateway-client.crt"
export GATEWAY_MTLS_PROFILE_INTERNAL_KEY_PATH="/run/secrets/gateway-client.key"
export GATEWAY_MTLS_PROFILE_INTERNAL_CA_PATH="/run/secrets/backend-ca.crt"

# Profile named "partner" — for external backend with separate cert chain
export GATEWAY_MTLS_PROFILE_PARTNER_CERT_PATH="/run/secrets/partner-gateway-client.crt"
export GATEWAY_MTLS_PROFILE_PARTNER_KEY_PATH="/run/secrets/partner-gateway-client.key"
export GATEWAY_MTLS_PROFILE_PARTNER_CA_PATH="/run/secrets/partner-ca.crt"
```

The env var naming convention is:

```
GATEWAY_MTLS_PROFILE_<NAME>_{CERT,KEY,CA}_PATH
```

Where `<NAME>` is the profile name in uppercase. The profile is selected per-revision via `backend_mtls_profile` in the policy.

**File contents:**

| Variable suffix | Expected content |
|---|---|
| `_CERT_PATH` | Path to PEM-encoded client certificate (public) |
| `_KEY_PATH` | Path to PEM-encoded client private key (keep secret) |
| `_CA_PATH` | Path to PEM-encoded CA certificate for verifying the backend's server certificate |

Files are loaded from the filesystem at gateway startup. In Kubernetes, mount these from a `Secret` volume:

```yaml
volumes:
  - name: mtls-certs
    secret:
      secretName: gateway-mtls-certs
volumeMounts:
  - name: mtls-certs
    mountPath: /run/secrets
    readOnly: true
```

## Environment Variable Reference

| Environment Variable | Default | Description |
|---|---|---|
| `GATEWAY_SERVER__ADMIN_TOKEN` | _(unset)_ | Admin token for management API. If unset, API is unauthenticated. |
| `DATABASE_URL` | _(required)_ | Full PostgreSQL connection URL including credentials. |
| `GATEWAY_CACHE__REDIS__URL` | `redis://127.0.0.1:6379` | Redis connection URL; may include password. |
| `GATEWAY_TLS_CERT_PATH` | _(unset)_ | Path to TLS certificate PEM for port 8443. Enables TLS when set. |
| `GATEWAY_TLS_KEY_PATH` | _(unset)_ | Path to TLS private key PEM for port 8443. Required with `GATEWAY_TLS_CERT_PATH`. |
| `GATEWAY_MTLS_PROFILE_<N>_CERT_PATH` | _(unset)_ | Client cert path for mTLS profile `<N>`. |
| `GATEWAY_MTLS_PROFILE_<N>_KEY_PATH` | _(unset)_ | Client key path for mTLS profile `<N>`. |
| `GATEWAY_MTLS_PROFILE_<N>_CA_PATH` | _(unset)_ | CA cert path for mTLS profile `<N>`. |
| `<jwt_secret_env value>` | _(per policy)_ | The actual JWT secret; name comes from `AuthPolicy.jwt_secret_env`. |
| `<jwt_public_key_env value>` | _(per policy)_ | The actual JWT public key PEM; name comes from `AuthPolicy.jwt_public_key_env`. |

## Using a Secrets Manager

The gateway reads all secrets from process environment variables. To use a secrets manager (HashiCorp Vault, AWS Secrets Manager, GCP Secret Manager, Azure Key Vault, etc.), inject the values into the process environment at startup. Common patterns:

| Platform | Injection mechanism |
|----------|---------------------|
| Kubernetes | [External Secrets Operator](https://external-secrets.io), CSI Secrets Store driver, or a sidecar that writes env vars |
| HashiCorp Vault | `vault agent` template that renders an env file consumed by the gateway process |
| AWS | ECS secret references, or Secrets Manager fetched at boot by an init container |
| GCP | Workload Identity + an init container fetching from Secret Manager |
| Docker (standalone) | `docker run --env-file` from a file rendered at deploy time, or Docker secrets mounted as files |

The principle is the same in every case: the secrets manager is responsible for delivering values to the environment; the gateway just reads them.

## What Goes in the Config File

The TOML config file (`config/default.toml`) is safe to commit. It should contain only:

```toml
[server]
proxy_port = 8080
management_port = 9090
# admin_token is set via GATEWAY_SERVER__ADMIN_TOKEN env var

[database]
max_connections = 20
min_connections = 5
# url is set via DATABASE_URL env var

[cache]
token_cache_ttl_secs = 300
# redis.url is set via GATEWAY_CACHE__REDIS__URL env var

[jwks]
fetch_timeout_ms = 5000
cache_ttl_secs = 3600
validate_on_reload = true
```

No secrets. No credentials. No keys. Only tunable parameters with safe defaults.

## Anti-Patterns to Avoid

| Anti-Pattern | Why It Is Dangerous | What to Do Instead |
|---|---|---|
| `jwt_secret = "mysecret"` in TOML | Committed to version control; visible to anyone with repo access | Use `jwt_secret_env = "MY_JWT_SECRET"` and set env var at runtime |
| `DATABASE_URL` in `config/default.toml` | Credentials in version control | Set `DATABASE_URL` as an environment variable only |
| Secrets in Dockerfile `ENV` directives | Baked into the image layer; visible in image history | Use runtime environment injection (Kubernetes Secrets, Docker secrets) |
| Secrets in CI/CD pipeline logs | CI logs are often broadly accessible | Mask secret variables in your CI system; never `echo $SECRET_VALUE` |
| Shared tokens across environments | Dev token leaks → prod access | Use separate secrets per environment |
| Tokens in Git history | Visible forever even after deletion | Rotate immediately; use `git filter-repo` if already committed |
| Plaintext secrets in token metadata | Stored in DB plaintext; appears in audit logs | Keep metadata to non-secret identifiers (IDs, plan names, regions) |
